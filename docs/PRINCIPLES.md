# 项目原则

这份文件写的是这个项目的工作规矩，Claude 和 Luna 都按它执行。用户的明确要求优先于这里的所有规则。

## 产品标准

- 功能真正可用、稳定、流畅、低功耗，并且没有安全隐患。
- 账号令牌、密钥和登录文件不进日志、报告、提交和发布包。测试不用真实账号。
- 诊断导出要能自己说明失败原因，不让用户或朋友再跑命令。预期事件缺失也要记录。
- 代码按当前支持的版本写。后台修复只改 `rust/`，`src/` 的 Node 后台已冻结，两个 VS Code 扩展继续用 JavaScript。

## 写代码

- 不做防御式编程。不为不会发生的情况加开关、兜底、兼容层或包装层。
- 只处理本项目的实际用法能走到的情况。理论上能构造，不算问题。
- 不写多余的测试和检查。测试要证明真实行为，不写重复的断言。
- 这些限制只约束修法，不约束排查。查问题时要查到底。
- 安全、数据迁移、校验和审阅不能因为上面几条省掉。删除数据、处理凭据和下载更新时，该有的检查要保留。
- 官方字段先找官方来源，比如 VS Code 扩展里带的前端代码。不靠猜，也不用日期或数量自己推算。

## 判断要有证据

- 报告里的结论必须来自真实运行。写不出来就写没有，不按验收词写死。
- 区分已确认和推断。没验证的说法标成推断，并写明怎么验证。
- 测试失败要写失败，部分完成要写部分完成。
- 看到 `passed=true` 还不够：要核对事件内容、版本号、文件 SHA 和时间。

## 验收

- 发布前必须用真实发布包走一遍：真实快捷方式、真实 VS Code 扩展、Remote-SSH、CLI、MCP、旧版升级，以及一键更新。
- 打包脚本不会编译 Rust，打包前要先 `cargo build --release`，并核对包内程序和当前提交一致。
- 涉及用户数据的功能，要用老数据验收，比如已压缩的旧对话。干净的新数据测不出这类问题。
- 同一时间只有一方跑验收。报告不能互相覆盖。
- 验收可以用脚本，但不能用脚本结果代替判断。代码审查和原始报告核对不能省。
- 验收脚本结束时删除自己创建的临时目录，长期测试环境除外。

## 发布

- 版本号和发布都由用户决定。发布前要经过审查。
- 提交留在本地，发布时才推送。工作流只在打标签时运行，不为验证随便跑 CI。
- 发布后要读线上 `release.json`，核对版本、提交和文件哈希。
- 发布说明写给下载的人看，不写个人信息。

## 分工

- 用户只和 Claude 沟通。Claude 负责规格、设计、审查和最终验收。
- Luna 按 `collab/` 下的清单实现和验收。清单写明范围、命令、预期结果、时长上限和止损线。
- 清单没写的事不做。不扩大范围，不顺手修别的，发现问题只报告。
- 清单里标 `[待确认]` 的内容，先核实再执行。清单不明确或命令报错，停下来问，不要猜，也不要自己改命令。
- 同一原因失败 2 次就停，把现象和原始报错发回来，不换思路绕过去。
- 不碰用户正在运行的切换器、VS Code、Codex 和真实配置。测试必须隔离。
- 信件和回复用简体中文，写得短，写结果。
